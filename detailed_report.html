AES-128 Image Encryption IP Core on Nexys 4 DDR
Complete Project Documentation

1. Project Objective

The goal is to build a complete System-on-Chip (SoC) on a Digilent Nexys 4 DDR FPGA board that encrypts a 64×64 grayscale image using AES-128 in CTR mode. The encrypted data is transmitted to a host PC via UART and reconstructed as a PNG image. This demonstrates hardware-software co-design where the computationally heavy AES algorithm runs in custom hardware while control logic runs in C on a soft processor.

4. Phase 1 — Vivado: Hardware Design

We used Xilinx Vivado 2024.2 to build the complete hardware system. Everything is automated by create_project.tcl.

4.1 Step 1: Packaging the Custom AES IP

Before building the system, we must package our custom Verilog AES core as a reusable Vivado IP block. The TCL script:

  1. Creates a temporary Vivado project and adds both Verilog files (aes128_core.v and aes128_axilite_wrapper.v)
  2. Sets aes128_axilite_wrapper as the top module
  3. Runs ipx::package_project to generate a component.xml file — this is the IP descriptor that Vivado reads
  4. Infers the AXI bus interface automatically from the port naming convention (S_AXI_*)
  5. Saves the IP and cleans up the temporary project

Why package as IP? Packaging allows us to drop our AES core into any Vivado Block Design just like Xilinx's own IPs. It also auto-generates the address mapping needed for software access.

4.2 Step 2: Creating the Vivado Project

The script creates a new project targeting xc7a100tcsg324-1 (Nexys 4 DDR), registers our custom IP repository path, and adds the pin constraint file.

4.3 Step 3: Building the Block Design

This is the core of the hardware. The Block Design (image_crypto_bd) contains 7 IP blocks connected via the AXI4-Lite bus:

4.3.1 — Clocking Wizard (clk_wiz_0)

What it does: Takes the 100 MHz board oscillator and generates a clean, stable output clock.
Why we need it: The raw board clock cannot be used directly — we need a PLL/MMCM to generate a phase-locked clock with proper reset synchronization. We configured it for 100 MHz output, but during implementation we discovered timing violations in the AES core's combinational key expansion logic. The solution was to reduce this to 25 MHz, giving 40ns of slack per clock cycle.
Key signals: clk_out1 (system clock to all IPs), locked (indicates PLL is stable), reset (active-high, connected to board reset button BTNR).

4.3.2 — MicroBlaze Processor (microblaze_0)

What it does: A 32-bit RISC soft-core CPU synthesized inside the FPGA fabric.
Why we need it: We need a programmable controller to: (a) manage the encryption loop, (b) handle button input, (c) perform XOR operations for CTR mode, and (d) format and transmit data over UART. Doing all this in pure Verilog state machines would be extremely complex.
Configuration: Barrel shifter enabled, hardware multiplier enabled, area-optimized, 32KB local memory (LMB), debug module for JTAG programming.
Automation: Vivado's apply_bd_automation automatically adds the Local Memory Bus (LMB), instruction/data BRAM, Processor System Reset block, and MicroBlaze Debug Module (MDM).

4.3.3 — AXI UART Lite (axi_uartlite_0)

What it does: Implements RS-232 serial communication at 115200 baud, 8 data bits, no parity (8N1).
Why we need it: This is our only communication channel to the host PC. The encrypted image data is transmitted as hex-encoded text lines over this UART.
How it connects: Its AXI slave port is connected to MicroBlaze's peripheral bus. Its TX/RX pins are routed to the FPGA pins D4 and C4 (connected to the on-board FTDI USB-UART bridge).
Software interface: MicroBlaze uses xil_printf() which internally writes to this IP's transmit FIFO register.

4.3.4 — AXI GPIO (axi_gpio_0)

What it does: Provides general-purpose I/O — 3-bit output (LEDs) and 2-bit input (buttons).
Why we need it: The user presses Button C (BTNC) to start encryption. LEDs provide visual status: LED0=waiting, LED16_R=running, LED16_G=done.
Configuration: Dual-channel GPIO. Channel 1: 3-bit output (LEDs). Channel 2: 2-bit input (buttons BTNC, BTND).
Register addresses: GPIO_DATA at offset 0x00, GPIO_TRI at 0x04, GPIO2_DATA at 0x08, GPIO2_TRI at 0x0C.

4.3.5 — AXI BRAM Controller 0 — Input Image (axi_bram_ctrl_0)

What it does: Provides AXI-accessible interface to a Block RAM that stores the input image.
Why we need it: The 64×64 grayscale image (4096 bytes) must be accessible to MicroBlaze. BRAM provides single-cycle read latency — much faster than external DDR.
Pre-loading: The BRAM is initialized with a .coe file (sample_64x64_gradient.coe) during synthesis, so the image is baked into the bitstream.
Base address: 0xC0000000, range 8KB.

4.3.6 — AXI BRAM Controller 1 — Output Storage (axi_bram_ctrl_1)

What it does: Provides a second BRAM for storing the encrypted output.
Why we need it: After encryption, ciphertext blocks are written here before being transmitted over UART. This allows the system to store the complete encrypted image on-chip.
Base address: 0xC2000000, range 8KB.

4.3.7 — Custom AES-128 IP (aes128_axilite_0)

What it does: Hardware AES-128 encryption engine accessible via memory-mapped registers.
Why we need it: This is the core accelerator. Software AES would take thousands of clock cycles per block; our hardware does it in 12 cycles.
Base address: 0x44A00000, range 4KB.

4.5 Step 5: Synthesis, Implementation, Bitstream

After building the block design, we validate it, generate the HDL wrapper, and run: (1) Synthesis — converts RTL to gate-level netlist, (2) Implementation — places and routes on the actual FPGA fabric, (3) Generate Bitstream — creates the .bit file that programs the FPGA.

Critical Fix: At 100 MHz, the AES key expansion logic created timing violations (negative slack). We reduced the clock to 25 MHz using the Clocking Wizard, which provided 40ns per cycle — enough for all combinational paths to settle.

4.6 Step 6: Export Hardware

File → Export → Export Hardware (Include Bitstream) generates image_crypto_bd_wrapper.xsa. This file packages the bitstream + hardware description and is consumed by Vitis to generate the Board Support Package (BSP).

5. The AES-128 Hardware Core — Deep Dive

5.1 Architecture (aes128_core.v)

The core implements FIPS-197 AES-128 encryption with a 3-state FSM:

  1. IDLE: Waits for start pulse. On start, expands the 128-bit key into 11 round keys (1408 bits) combinationally, and performs the initial AddRoundKey (XOR with round key 0).
  2. RUNNING: Executes rounds 1–10. Each clock cycle performs one round: SubBytes → ShiftRows → MixColumns → AddRoundKey. Round 10 skips MixColumns per the AES specification.
  3. DONE: Latches the output and pulses done for one cycle.

Total latency: 12 clock cycles (1 for key expand + initial ARK, 9 for rounds 1-9, 1 for round 10, 1 for output latch).

5.2 Key Internal Functions

FunctionPurpose
sbox_f256-entry lookup table implementing the AES S-Box (SubBytes)
xtime_fGalois Field multiplication by 2 — used in MixColumns
sub_word / rot_wordUsed in key expansion (SubWord applies S-Box to 4 bytes, RotWord rotates a word left by 1 byte)

5.3 AXI-Lite Wrapper (aes128_axilite_wrapper.v)

This module wraps the AES core with a standard AXI4-Lite slave interface so MicroBlaze can access it via memory-mapped registers:

6. Phase 2 — Vitis: Software Development

6.1 What is Vitis and Why We Need It

Vitis Unified IDE is Xilinx's software development environment. Since we have a MicroBlaze CPU inside our FPGA, we need to write C code for it. Vitis takes the .xsa file from Vivado and:

  1. Reads the hardware description to understand what peripherals exist and at what addresses
  2. Generates xparameters.h — a header file containing all base addresses as C macros
  3. Builds a Board Support Package (BSP) with low-level drivers (xil_io.h, xil_printf.h)
  4. Compiles our C code using the MicroBlaze cross-compiler (mb-gcc)
  5. Produces an .elf executable that runs on MicroBlaze

6.2 Platform Component

We created aes_platform pointing to image_crypto_bd_wrapper.xsa. This generated the BSP with standalone OS for microblaze_0. The platform build produces all necessary driver libraries.

6.3 Application Component

We created aes_app as an Empty Application and imported two files:

6.3.1 — Software Driver (aes_ip_driver.h)

This header provides inline functions to interact with our AES IP:

  • AES_WriteKey(key[16]) — Writes the 128-bit key to registers KEY_W0–W3, converting byte array to 32-bit words with big-endian byte packing
  • AES_WriteDataIn(blk[16]) — Writes 128-bit plaintext to DIN registers
  • AES_Start() — Writes 1 to CTRL register bit 0, which pulses the start signal in hardware
  • AES_WaitDone() — Polls STATUS register bit 0 in a spin loop until DONE=1
  • AES_ReadDataOut(out[16]) — Reads 128-bit ciphertext from DOUT registers

All register access uses Xil_Out32() and Xil_In32() which perform memory-mapped I/O writes/reads.

6.3.2 — Main Application (main.c)

The firmware implements AES-128 in CTR (Counter) mode:

  1. Initialize GPIO: Configure LED pins as output, button pins as input
  2. Wait for BTNC: LED0 lights up. CPU spins until center button is pressed (with debounce)
  3. Write AES Key: The demo key 000102030405060708090A0B0C0D0E0F is written once
  4. Encryption Loop (256 iterations):
    • Read 16 bytes from Input BRAM at offset block_index × 16
    • Send the current counter value to AES IP (not the plaintext — this is CTR mode)
    • Start AES encryption and wait for done
    • Read the encrypted counter (keystream) from AES output
    • XOR keystream with plaintext → produces ciphertext
    • Write ciphertext to Output BRAM
    • Increment counter (big-endian, byte 15 is LSB)
    • Print BLOCK NNN: <32 hex chars> over UART
  5. Done: LED16_G turns green, prints "DONE"
Why CTR Mode? CTR mode XORs plaintext with an encrypted counter, meaning: (a) we only need the encryption direction (no inverse S-Box needed), (b) identical plaintext blocks produce different ciphertext (unlike ECB which leaks patterns), (c) decryption is the same operation as encryption.

7. Phase 3 — Python Scripts: Host-Side Tools

7.1 UART Capture (uart_capture.py)

Opens the serial port (e.g., COM4) at 115200 baud. Waits for lines from the FPGA. Parses each BLOCK NNN: HHHH... line, extracts the 16-byte hex data, and assembles all 256 blocks into a 4096-byte raw file. Finally, reconstructs a 64×64 grayscale PNG from the raw bytes.

7.2 Verification (compare_results.py)

Compares the FPGA-produced ciphertext byte-by-byte against a software-generated golden reference (produced by Python's cryptography library). Reports match percentage, pinpoints first mismatch location, and generates a side-by-side comparison PNG.

11. How to Explain This to Your Professor

  1. Start with the problem: "We need to encrypt image data using AES-128 on an FPGA for high-speed, hardware-accelerated security."
  2. Show the architecture: "We built a System-on-Chip with a MicroBlaze CPU, custom AES IP, dual BRAMs, GPIO, and UART — all connected via AXI4-Lite bus."
  3. Explain the custom IP: "Our AES core implements all 10 rounds of FIPS-197 in Verilog, completing encryption in 12 clock cycles per 128-bit block."
  4. Show the software: "The C firmware implements CTR mode — it encrypts counter values using the hardware IP and XORs the result with plaintext."
  5. Discuss the challenge: "We encountered timing violations due to combinational key expansion and solved it by reducing the clock to 25 MHz."
  6. Show verification: "We verified correctness by comparing FPGA output byte-by-byte against a Python-generated golden reference."
